TASK: Phase 4 / P1 — Generated-media contract and deterministic unit resolution

MODEL / REASONING / USAGE
- Recommended configuration: `Terra High`.

VERSIONING
- This prompt's assigned project version is `0.4.1`.

CONTEXT

Read BOOT.md first, then README.md, AGENTS.md, docs/README.md, docs/architecture.md, docs/template-system.md, docs/roadmap/initial-roadmap.md, the completed Phase 3 implementation/tests, and the current AssemblyTemplate/ClipPlan/story-workspace boundaries before editing.

Phase 3 is owner-closed after P4 at 0.3.4. Its live Google closeout smoke was explicitly waived; do not rewrite history or claim that inherited live-provider qualification happened.

Phase 4 realizes only the generated media required by the selected AssemblyTemplate. It must not invent a second ProductionPlan, shot plan, media-selection stage, or template-specific story interpretation layer.

The current default template declares generated roles on segments:

    hook 0-5
      opening-anchor (presenter)
      <- hook + headline

    content 5-15
      content-video (video)
      content-voiceover (voiceover)
      <- narration

    support 15-28
      supporting-anchor (presenter)
      <- supporting-information

    closing 28-40
      supporting-anchor (presenter)
      <- closing

One generated role may therefore be referenced by multiple segments. Treat each segment-role reference as its own deterministic generated-media unit. Do not collapse the two supporting-anchor references into one 25-second creative asset and do not add a model call to decide how to split them.

GOAL

Create the provider-neutral generated-media contract and deterministic resolver that expands a validated AssemblyTemplate plus validated ClipPlan into ordered per-segment generated-media units.

Also expose the smallest ClipPlan artifact-validation helper needed by a later on-disk media workflow without reconstructing StoryInput.

SCOPE

Implement:
- provider-neutral generated-media unit types;
- deterministic AssemblyTemplate + ClipPlan -> generated-media-unit resolution;
- provider-neutral video and speech generation request/result/client contracts;
- deterministic generated-media input identity helpers where they belong in core;
- a narrow persisted ClipPlan validation-by-identity export;
- focused generic/default-template tests;
- version/test wiring.

Do not implement any provider call, binary persistence, CLI media command, Veo adapter, TTS adapter, FFmpeg behavior, or live qualification in this task.

IMPLEMENTATION REQUIREMENTS

1. One unit per segment-role reference.
   - Resolve units by iterating template segments in declared order, then each segment's generatedAssetRoles in declared order.
   - Create exactly one GeneratedMediaUnit for every generated role reference on a segment.
   - A generated role referenced by two segments becomes two units.
   - Do not merge adjacent segments or repeated role IDs.
   - Do not create units for standardized intro/outro roles.
   - Do not create units for content slots that have no generated role reference.

2. Stable safe unit identity.
   - Unit IDs must be deterministic, ordered, and safe for local filenames.
   - Prefer ordinal engine-owned IDs such as `u01`, `u02`, ... rather than deriving filenames from untrusted template role/segment IDs.
   - Preserve the original segment ID and role ID as metadata.
   - Unit identity must not depend on provider model/job IDs or filesystem locations.

3. Unit contract.
   Each resolved unit should expose only deterministic production requirements such as:
   - unitId;
   - segment { id, startSeconds, endSeconds };
   - role { id, kind };
   - targetDurationSeconds derived exactly from segment timing;
   - ordered referenced content values with slot id, usage, and validated ClipPlan text;
   - spokenText derived only from referenced slots whose template usage is `spoken`.

   Keep the contract small and JSON-safe.
   Do not include:
   - provider prompt text;
   - provider-specific model parameters;
   - camera directions;
   - shot lists;
   - transition choices;
   - final codec/frame-rate claims;
   - source/publisher URLs;
   - generated bytes.

4. Slot linkage.
   - Resolve segment contentSlots through the validated template and validated ClipPlan.
   - Preserve segment content-slot order.
   - Include display-slot text as deterministic unit context when the segment references it.
   - `spokenText` must concatenate only spoken slots, in segment slot order, without rewriting their text.
   - If a voiceover unit has no non-blank spokenText, fail deterministically.
   - Presenter units may carry display context in addition to spokenText, but display text must not silently become dialogue.
   - Video-only units may have context with no spokenText.

5. Default-template proof.
   The default template must resolve exactly these five ordered units:

       u01 hook / opening-anchor / presenter / 5 sec
       u02 content / content-video / video / 10 sec
       u03 content / content-voiceover / voiceover / 10 sec
       u04 support / supporting-anchor / presenter / 13 sec
       u05 closing / supporting-anchor / presenter / 12 sec

   Their content linkage must come from template data:
   - u01: hook + headline, spokenText from hook only;
   - u02/u03: narration;
   - u04: supporting-information;
   - u05: closing.

   Do not hard-code these IDs in the resolver.

6. Generic-template proof.
   - Preserve the existing synthetic non-default/non-40-second template behavior.
   - Add generated-media resolution proof using arbitrary slot, segment, and role IDs.
   - Generic resolution must work without source changes when the synthetic template shape changes within the existing AssemblyTemplate contract.

7. Provider-neutral client boundaries.
   Add thin contracts, likely in `src/core/generated-media.ts` or similarly narrow modules, for:
   - VideoGenerationClient;
   - SpeechGenerationClient;
   - their provider-neutral requests/results.

   Requests should carry only inputs VidGen owns, for example:
   - media unit identity/kind;
   - target duration;
   - deterministic content/spoken text;
   - optional approved reference-image blobs for presenter generation;
   - no arbitrary provider endpoint.

   Results should carry only minimal provenance plus generated bytes/format facts needed for story-local persistence, for example:
   - provider;
   - model;
   - request/operation IDs when available;
   - MIME type;
   - bytes;
   - provider-reported or nominal duration when known.

   Do not expose raw Google/provider envelopes through core/application code.

8. Approved reference-image boundary.
   - Define a provider-neutral in-memory reference-image value sufficient for later presenter generation.
   - It may carry MIME type, bytes, and a VidGen-computed SHA-256 identity.
   - It must not carry an untrusted remote URL as the normal provider interface.
   - Do not load files or fetch images in P1.

9. Persisted ClipPlan consumer capability.
   Phase 4 will consume `clip-plan.json` from an existing planned story workspace, but `validateClipPlan()` currently requires a full StoryInput only to establish the expected story fingerprint.

   Add a narrow ClipPlan-owned export that validates a durable ClipPlan against:
   - an expected storyFingerprint string; and
   - the selected validated AssemblyTemplate.

   Requirements:
   - preserve all existing strict ClipPlan shape/order/text/template checks;
   - preserve the existing `validateClipPlan(value, storyInput, template)` API by delegating to the new identity-oriented validator where practical;
   - do not duplicate ClipPlan semantics in the Phase 4 application layer;
   - do not weaken identity validation.

10. Deterministic identities.
   - Reuse canonicalJson + SHA-256 patterns already present in the repository.
   - If adding a generated-media-unit or request-input fingerprint helper, define exactly which VidGen-owned semantic fields participate.
   - Do not hash raw provider response envelopes.
   - Provider/model/reference-image identities can participate later when the effective generation input is built; do not prematurely freeze provider-specific cache identity in the template contract.

11. Errors.
   - Reuse existing VidGen error categories where they are sufficient.
   - Add a narrow generated-media-owned error code only if a caller truly needs a distinct stable recovery path.
   - Public errors must not dump ClipPlan text, reference bytes, or future provider prompts.

12. Version/test wiring.
   - Set package.json and src/version.ts to 0.4.1.
   - Keep package-lock.json absent.
   - Add focused tests to the normal `npm test` / `npm run check` path.

FOCUSED TESTS

Prove:
- default-news-40s resolves exactly five ordered per-segment role units with the timing/content linkage listed above;
- the repeated supporting-anchor role becomes two separate units;
- spokenText includes only spoken slots and never promotes the display headline to dialogue;
- a voiceover role without usable spoken content fails;
- arbitrary non-default segment/role/slot IDs resolve generically;
- a non-40-second synthetic template remains supported;
- no default slot/role/segment IDs are hard-coded into core resolution logic;
- unit IDs are stable and safe for filenames;
- persisted ClipPlan validation-by-identity preserves the same strictness as the StoryInput-based validator;
- wrong story fingerprint or template identity still fails;
- provider-neutral requests/results do not include Google-specific fields or provider URLs.
