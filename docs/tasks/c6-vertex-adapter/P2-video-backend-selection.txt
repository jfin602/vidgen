TASK: Correction 6 / P2 — Video backend selection

MODEL / REASONING / USAGE
- Recommended configuration: `Terra High`.

VERSIONING
- Required unchanged project version: `0.6.5`.

GOAL

Wire the P1 Vertex adapter into the existing simple and cinematic video-generation consumers through one explicit runtime backend selector while preserving the current Developer API backend as the default.

Read P1's resulting source/tests and trace both default video-client construction sites, provider/model fingerprints, durable provenance, dependency-injection seams, and CLI behavior before editing.

MUST REMAIN TRUE

- Add one runtime selector `VIDGEN_VIDEO_BACKEND` with supported values `developer` and `vertex`.
- Omitted `VIDGEN_VIDEO_BACKEND` must preserve current behavior by selecting the existing Developer API Veo client.
- `developer` uses the existing Developer API configuration and must not require any Vertex project/location/model/ADC state.
- `vertex` constructs the P1 Vertex adapter and must not require `GEMINI_API_KEY` for video generation.
- Invalid/blank backend configuration fails clearly before provider work. Never fall back from one backend to the other after configuration, auth, request, polling, or provider failure.
- Use one small shared factory/selector consumed by both the cinematic media workflow and simple headline workflow. Do not duplicate selection logic and do not introduce a generalized provider registry/framework.
- Preserve each workflow's existing `createVideoClient` injection seam so tests and callers can still supply a neutral fake directly.
- Do not add a CLI flag for backend selection; backend choice remains runtime environment configuration.
- Preserve current simple copy/duration/speech timing, FFmpeg finishing, failure-honest MP4/JSON publication, and sidecar schema.
- Preserve current cinematic GeneratedMediaUnit resolution, media-run resume behavior, generated-media schema, story-local reuse, and assembly behavior.
- Backend identity must affect expensive-media reuse/provenance through the existing neutral provider/model identity. Switching Developer API <-> Vertex must not reuse an asset generated by the other backend.
- Existing durable structures should remain unchanged if their generic provider/model fields already distinguish the effective backend. Do not add Vertex-specific durable fields or leak project IDs, locations, ADC state, access tokens, raw responses, or staging URIs.
- The existing Developer API provider/model provenance must remain byte-for-byte/semantically compatible for existing runs.
- No automatic fallback, retry across backends, or dual generation.
- Package and engine version remain 0.6.5.

PROOF

Focused tests must prove:
- omitted backend selects the existing Developer API client;
- explicit `developer` is equivalent to the existing default and does not inspect Vertex-only configuration;
- explicit `vertex` selects the Vertex adapter without requiring the Developer API key;
- invalid backend fails before either provider is called;
- headline default construction uses the selector while injected fake clients bypass it;
- cinematic media default construction uses the selector while injected fake clients bypass it;
- headline sidecar provider/model provenance distinguishes Vertex safely without schema changes;
- cinematic generated-media provenance/fingerprints distinguish Vertex from Developer API and switching backend invalidates story-local reuse;
- no credential/project/location leakage enters simple sidecars, cinematic manifests, public errors, or fingerprints beyond the already-approved safe provider/model identity;
- existing CLI parsing/help and Developer API workflows remain unchanged.

Run focused selector/headline/media/generated-media/Developer-Veo/Vertex tests, `npm test`, `npm run check`, `node src/cli.ts --help`, and `git diff --check`.
