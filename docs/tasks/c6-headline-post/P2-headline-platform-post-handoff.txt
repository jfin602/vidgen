TASK: Correction 6 / P2 — Headline platform post handoff

MODEL / REASONING / USAGE
- Recommended configuration: `Terra High`.

VERSIONING
- Required unchanged project version: `0.6.5`.

GOAL

Add a fresh VidGen CLI command that generates one simple headline clip and hands that same completed clip/caption to one or more explicitly selected publishing networks through the independently installed VidGen Poster. Keep every platform implementation owned by jfin602/vidgen-poster.

Start from the P1 dry-run result. Inspect the current VidGen CLI/headline result contract and the current VidGen Poster CLI/platform contract before editing. Do not import Poster source code or reimplement platform behavior.

MUST REMAIN TRUE

- Add `vidgen headline-post` with the same headline generation inputs as `vidgen headline`, including `--dry-run`, plus repeatable `--platform <bluesky|meta|x>`.
- `--platform` is required and may be supplied one to three times, matching the existing repeatable-option style used by `--anchor-reference`. Each occurrence contains exactly one platform value; comma-separated values are not supported.
- Accepted platform values are exactly `bluesky`, `meta`, and `x`. Preserve the user's platform order. Reject missing platforms, more than three occurrences, duplicate platform selections, empty values, comma-packed values, or unsupported names before provider generation or Poster process activity.
- For every selected platform, invoke Poster readiness as `doctor <platform>`. All selected platforms must pass doctor before the one expensive headline generation begins. If any doctor fails or the configured Poster build does not support a selected platform, stop before generation; do not fallback, silently drop a platform, or fake readiness.
- Current Poster support remains runtime truth. In particular, do not claim X operational support unless the configured Poster build actually supports and qualifies `x`.
- After every selected platform passes doctor, run the existing normal headline generation exactly once. Poster posting may begin only after the finished MP4 and coupled sidecar reach the existing successful headline publication boundary.
- Post the same finished MP4 and exact same caption sequentially in the supplied platform order using the equivalent of `post <platform> --video <finished-mp4> --text <caption>`.
- Caption text for every platform is exactly `"<headline>" by <source display name>`, using the same governed Article/source identity that produced the clip. Do not summarize, rewrite, add hashtags, or generate platform-specific social copy.
- A failure while posting one platform must not delete valid VidGen output or erase already completed platform outcomes. Continue down the remaining requested platform list without retrying the failed platform automatically. The overall command must return nonzero if any requested platform failed, while reporting bounded per-platform success/failure status without exposing raw child output.
- Platform-specific authentication, validation, upload, duplicate protection, receipts, API behavior, retries, and capability support remain entirely owned by VidGen Poster. VidGen contains only strict platform-list parsing and orchestration.
- The Poster installation root is runtime configuration via `VIDGEN_POSTER_ROOT`; do not hardcode a deployment path.
- Invoke Poster only as an external process from the configured Poster repository/runtime using argument-vector execution with no shell interpolation. Platform values, headline/source text, and paths are untrusted values and must remain discrete arguments.
- A real run must not pass Poster `--dry-run`.
- `headline-post --dry-run` requires the same one-to-three platform list, runs `doctor` for every selected platform, then runs the P1 headline dry-run contract once. It still performs structured-text presenter-copy generation and persists P1 inspection artifacts, but suppresses Veo and must never invoke Poster `post`, upload media, or create an external post.
- If headline generation fails, no Poster post may run for any platform.
- Do not forward or persist raw child stdout/stderr as trusted diagnostics. No secrets, authorization data, tokens, raw provider responses, or shell command strings may enter VidGen artifacts or public errors.
- Do not add a VidGen `--allow-duplicate` path; Poster remains the duplicate/publication authority.
- Existing `headline`, its P1 dry-run behavior, and all cinematic commands remain unchanged.
- Package and engine version remain 0.6.5.

PROOF

Focused tests must cover:
- parsing/help for one, two, and three repeatable `--platform` occurrences;
- valid ordered examples including `--platform x`, `--platform x --platform meta`, `--platform bluesky --platform x`, and all three platforms;
- missing, fourth, duplicate, comma-packed, empty, malformed, and unsupported platform values fail before provider/Poster activity;
- platform order is preserved exactly;
- all selected doctors run before generation and any doctor failure prevents generation and every post;
- dry run doctors every selected platform, performs structured-text generation once, produces P1 inspection artifacts, and never calls Veo or Poster post;
- normal generation occurs exactly once regardless of one, two, or three selected platforms;
- after final headline readiness, the same video path and exact caption are passed to Poster once per selected platform in supplied order;
- exact caption values containing whitespace, quotes, or shell-significant characters remain one `--text` argument with no shell interpretation;
- one platform post failure does not stop attempts to later selected platforms, does not retry automatically, preserves the finished MP4/sidecar, and makes the overall command fail safely;
- generation failure invokes no platform posts;
- no publishing credentials or raw child output are persisted/exposed;
- existing headline and cinematic CLI regression coverage remains green.

Run focused CLI/headline/handoff tests, `npm run check`, `node src/cli.ts --help`, and `git diff --check`.

NON-GOALS
